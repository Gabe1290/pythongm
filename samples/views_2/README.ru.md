# Views — Уровень 2

Демонстрация **кооператива с разделённым экраном**: комната 2400×800
показана как две камеры рядом в одном окне 800×600. **Левая
половина** (view 0) следует за **игроком 1** (оранжевый, клавиши со
стрелками); **правая половина** (view 1) следует за **игроком 2**
(бирюзовый, WASD). Каждый игрок исследует общую комнату в своей
полосе и собирает монеты — вы наблюдаете за обоими одновременно.

**Куда это вписывается:** второй уровень четвёртой семьи образцов.
`views_1` ввела одну камеру с прокруткой; `views_2` вводит
**несколько viewport'ов одновременно** — другую ключевую возможность
views GameMaker. См.
[`../README.md`](../README.md#progression-how-each-family-is-built-not-just-how-it-plays)
для полного прогресса. Движение повторно использует идиому сетки из
`maze_1`/`views_1`.

**Звук и музыка:** отсутствуют — ни одного звукового файла не
добавлено к этому образцу.

## Как играть

- **Игрок 1 (оранжевый):** клавиши со стрелками — двигается в
  **левой** view.
- **Игрок 2 (бирюзовый):** `W` `A` `S` `D` — двигается в **правой**
  view.
- Оба двигаются на одну клетку сетки (32px) за раз; стены
  (`obj_wall`) твёрдые. Центральный разделитель с отверстиями
  разделяет две полосы.
- **Цель:** соберите 18 монет (`obj_coin`) — любой игрок может
  схватить любую монету; каждая стоит 10 очков (показано в заголовке
  окна).

## Почему два игрока останавливаются независимо (настоящая ловушка)

Движение в сетке обычно останавливается на событии `nokey`
(срабатывает, когда *ни одна* клавиша не нажата). Но состояние
клавиш отслеживается глобально по всем экземплярам, поэтому с двумя
игроками `nokey` срабатывает лишь когда **оба** отпускают всё —
игрок 2 продолжал бы скользить, пока игрок 1 держит клавишу. Поэтому
каждый игрок вместо этого останавливается через **`keyboard_release`**
для **своих собственных** клавиш (стрелки для P1, WASD для P2),
которая срабатывает по клавише и по объекту. Это отличие от одного
игрока `views_1`, который может безопасно использовать `nokey`.

## Как настроен разделённый экран

Невидимый контроллер, `obj_camera`, конфигурирует обе views в своём
событии **create** (зарегистрированный `enable_views` + два действия
`set_view`), и та же конфигурация запечена в блок `views` комнаты для
правильности в кадре 0 при экспорте:

- **view 0** — `view`/`port` `400×600`, `port_x` 0 (левая половина),
  `follow` `obj_player1`.
- **view 1** — `view`/`port` `400×600`, `port_x` 400 (правая
  половина), `follow` `obj_player2`.

Обе views — **1:1** (размер view == размер порта) и разделены
**влево/вправо** (`port_y` 0, полная высота). Это важно для
согласованности между целями: настольный и HTML5 рендерят каждую
view в 1:1 (обрезают + смещают, они **не** масштабируют view к
порту), и разделение влево/вправо избегает инверсии `port_y` между
Kivy (y-вверх) и настольным/HTML5 (y-вниз). Уменьшенный мини-карта
обзор (view больше своего порта) намеренно **не** используется
здесь — он масштабировался бы правильно только на Kivy.

## Объекты

| Объект | Роль | Ключевые события |
|---|---|---|
| `obj_camera` | Невидимый контроллер; включает + конфигурирует обе views | create (`enable_views`, 2× `set_view`) |
| `obj_player1` | Игрок левой view (стрелки) | keyboard (up/down/left/right/nokey), keyboard_release (по клавише), collision_with_obj_wall |
| `obj_player2` | Игрок правой view (WASD) | keyboard (w/a/s/d/nokey), keyboard_release (по клавише), collision_with_obj_wall |
| `obj_coin` | Предмет для сбора стоимостью 10 | collision_with_obj_player1, collision_with_obj_player2, destroy (`set_score` +10) |
| `obj_wall` | Статичная твёрдая стена / граница камеры | (нет — только пассивный коллайдер) |

## Ресурсы

4 спрайта (`spr_player1`, `spr_player2`, `spr_wall`, `spr_coin`,
каждый 32×32, один кадр, точный до пикселя), 0 звуков. Всё искусство
сплошного цвета CC0, созданное для этого образца — см. `CREDITS.txt`.

## Что можно настроить

- **Направление разделения** — этот образец использует разделение
  влево/вправо (`port_x` 0 и 400, `port_y` 0, полная высота).
  Разделение сверху/снизу поместило бы половины на разные `port_y`;
  обратите внимание, что это рендерится в другой вертикальной
  позиции на Kivy (y-вверх) против настольного/HTML5 (y-вниз),
  поэтому влево/вправо — переносимый выбор.
- **Ширина view** — каждая view шириной `400` (половина окна).
  Расширьте окно или сузьте views, чтобы изменить, сколько комнаты
  видит каждый игрок.
- **Границы** — `hborder` 120 / `vborder` 150 устанавливают мёртвую
  зону каждой камеры.

## Статус экспорта

- **Настольный (pygame):** эталон —
  `tests/test_views_2_sample.py` загружает образец, выполняет событие
  create `obj_camera`, и подтверждает, что две камеры прокручиваются
  **независимо** (движение одного игрока не двигает view другого) и
  фиксируются на границе комнаты, плюс подсчёт очков за монеты и
  остановка `keyboard_release` для каждого игрока.
- **Веб (HTML5):** `engine.js` рендерит каждую видимую view (обрезка
  по view + перемещение 1:1); конфигурация двух views переносится в
  экспорт.
- **Мобильный (Kivy/Android):** экспортёр рендерит комнату в Fbo и
  копирует область каждой видимой view в её порт экрана
  (`tests/test_kivy_views.py` покрывает рендеринг нескольких views).
  Действия `enable_views`/`set_view` выведены, поэтому настройка
  двух views работает из события create `obj_camera`, так же как и
  из запечённой конфигурации комнаты. Остаточное ограничение (как в
  `views_1`): цель рендеринга строится при создании комнаты, поэтому
  `views_enabled` должна быть в конфигурации комнаты (здесь есть) для
  того, чтобы камера рендерила на Kivy.
- Согласованность математики прокрутки между целями закреплена
  `tests/test_views_export_parity.py`.

Выставлено на вкладке Welcome редактора как "Views — Level 2"
(`widgets/welcome_tab.py`).
