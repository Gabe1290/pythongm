# Views — Рівень 2

Демонстрація **кооперативу з розділеним екраном**: кімната 2400×800
показана як дві камери поруч в одному вікні 800×600. **Ліва половина**
(view 0) слідує за **гравцем 1** (помаранчевий, клавіші зі стрілками);
**права половина** (view 1) слідує за **гравцем 2** (бірюзовий,
WASD). Кожен гравець досліджує спільну кімнату у своїй смузі й
збирає монети — ви спостерігаєте за обома одночасно.

**Куди це вписується:** другий рівень четвертої родини зразків.
`views_1` запровадила одну камеру з прокруткою; `views_2` запроваджує
**кілька viewport'ів одночасно** — іншу ключову можливість views
GameMaker. Див.
[`../README.md`](../README.md#progression-how-each-family-is-built-not-just-how-it-plays)
для повного прогресу. Рух повторно використовує ідіому сітки з
`maze_1`/`views_1`.

**Звук і музика:** відсутні — жодного звукового файлу не додано до цього зразка.

## Як грати

- **Гравець 1 (помаранчевий):** клавіші зі стрілками — рухається в
  **лівій** view.
- **Гравець 2 (бірюзовий):** `W` `A` `S` `D` — рухається в **правій**
  view.
- Обидва рухаються на одну клітинку сітки (32px) за раз; стіни
  (`obj_wall`) тверді. Центральний розділювач з отворами розділяє
  дві смуги.
- **Мета:** зберіть 18 монет (`obj_coin`) — будь-який гравець може
  схопити будь-яку монету; кожна варта 10 очок (показано в заголовку
  вікна).

## Чому два гравці зупиняються незалежно (справжня пастка)

Рух у сітці зазвичай зупиняється на події `nokey` (спрацьовує, коли
*жодна* клавіша не натиснута). Але стан клавіш відстежується глобально
по всіх екземплярах, тому з двома гравцями `nokey` спрацьовує лише
коли **обидва** відпускають усе — гравець 2 продовжував би ковзати,
поки гравець 1 тримає клавішу. Тому кожен гравець натомість
зупиняється через **`keyboard_release`** для **своїх власних** клавіш
(стрілки для P1, WASD для P2), яка спрацьовує по клавіші й по об'єкту.
Це відмінність від одного гравця `views_1`, який може безпечно
використовувати `nokey`.

## Як налаштований розділений екран

Невидимий контролер, `obj_camera`, конфігурує обидві views у своїй
події **create** (зареєстрований `enable_views` + дві дії `set_view`),
і та сама конфігурація запечена в блок `views` кімнати для
правильності в кадрі 0 при експорті:

- **view 0** — `view`/`port` `400×600`, `port_x` 0 (ліва половина),
  `follow` `obj_player1`.
- **view 1** — `view`/`port` `400×600`, `port_x` 400 (права половина),
  `follow` `obj_player2`.

Обидві views — **1:1** (розмір view == розмір порту) і розділені
**ліворуч/праворуч** (`port_y` 0, повна висота). Це важливо для
узгодженості між цілями: настільний і HTML5 рендерять кожну view в
1:1 (обрізають + зміщують, вони **не** масштабують view до порту), і
розділення ліворуч/праворуч уникає інверсії `port_y` між Kivy
(y-вгору) та настільним/HTML5 (y-вниз). Зменшений мінікарта-огляд
(view більший за свій порт) навмисно **не** використовується тут —
він масштабувався б правильно лише на Kivy.

## Об'єкти

| Об'єкт | Роль | Ключові події |
|---|---|---|
| `obj_camera` | Невидимий контролер; вмикає + конфігурує обидві views | create (`enable_views`, 2× `set_view`) |
| `obj_player1` | Гравець лівої view (стрілки) | keyboard (up/down/left/right/nokey), keyboard_release (по клавіші), collision_with_obj_wall |
| `obj_player2` | Гравець правої view (WASD) | keyboard (w/a/s/d/nokey), keyboard_release (по клавіші), collision_with_obj_wall |
| `obj_coin` | Предмет для збору вартістю 10 | collision_with_obj_player1, collision_with_obj_player2, destroy (`set_score` +10) |
| `obj_wall` | Статична тверда стіна / межа камери | (немає — лише пасивний колайдер) |

## Ресурси

4 спрайти (`spr_player1`, `spr_player2`, `spr_wall`, `spr_coin`,
кожен 32×32, один кадр, точний до пікселя), 0 звуків. Усе мистецтво
суцільного кольору CC0, створене для цього зразка — див.
`CREDITS.txt`.

## Що можна налаштувати

- **Напрямок розділення** — цей зразок використовує розділення
  ліворуч/праворуч (`port_x` 0 і 400, `port_y` 0, повна висота).
  Розділення зверху/знизу помістило б половини на різні `port_y`;
  зверніть увагу, що це рендериться на іншій вертикальній позиції на
  Kivy (y-вгору) проти настільного/HTML5 (y-вниз), тому
  ліворуч/праворуч — переносний вибір.
- **Ширина view** — кожна view шириною `400` (половина вікна).
  Розширте вікно або звузьте views, щоб змінити, скільки кімнати бачить
  кожен гравець.
- **Межі** — `hborder` 120 / `vborder` 150 встановлюють мертву зону
  кожної камери.

## Статус експорту

- **Настільний (pygame):** еталон —
  `tests/test_views_2_sample.py` завантажує зразок, виконує подію
  create `obj_camera`, і підтверджує, що дві камери прокручуються
  **незалежно** (рух одного гравця не рухає view іншого) і фіксуються
  на межі кімнати, плюс підрахунок очок за монети й зупинка
  `keyboard_release` для кожного гравця.
- **Веб (HTML5):** `engine.js` рендерить кожну видиму view (обрізання
  по view + переміщення 1:1); конфігурація двох views переноситься в
  експорт.
- **Мобільний (Kivy/Android):** експортер рендерить кімнату у Fbo й
  копіює область кожної видимої view в її порт екрана
  (`tests/test_kivy_views.py` покриває рендеринг кількох views). Дії
  `enable_views`/`set_view` виведені, тому налаштування двох views
  працює з події create `obj_camera`, так само як і з запеченої
  конфігурації кімнати. Залишкове обмеження (як у `views_1`): ціль
  рендерингу будується при створенні кімнати, тому `views_enabled` має
  бути в конфігурації кімнати (тут є) для того, щоб камера рендерила на
  Kivy.
- Узгодженість математики прокрутки між цілями закріплена
  `tests/test_views_export_parity.py`.

Виставлено на вкладці Welcome редактора як "Views — Level 2"
(`widgets/welcome_tab.py`).
