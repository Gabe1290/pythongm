# Sky Strike — Level 1

A vertical-scrolling shoot-'em-up in the spirit of classic arcade
shooters like *Xevious*: fly north over scrolling ground, shoot down
enemy planes with bullets, and bomb ground targets you can't hit with
bullets at all — two separate weapons for two separate kinds of enemy.

**Nothing new was added to the engine for this sample.** Every mechanic
here — the scrolling ground, the two weapon types, the wave spawning,
the win/lose loop — is built entirely from actions that already
existed: `set_background`'s tiling/scroll speed, `create_instance`,
`set_alarm`, `set_hspeed`/`set_vspeed`, and ordinary
`collision_with_<object>` events. It's a good example of how far the
existing action set goes without a dedicated extension.

## How to play

- **Arrow keys / WASD** move the ship (clamped to the screen — you can't
  fly off the edges).
- **Space** fires bullets straight up. Hold it down for rapid fire (a short
  per-shot cooldown, not literally every frame). Bullets only hit
  **enemy planes**.
- **Z** drops a bomb. Bombs keep the ship's forward momentum — they
  travel *up* the screen (the same direction you're flying), slower than
  bullets, toward whatever ground target is ahead of you when you drop.
  A small crosshair drawn ahead of the ship shows the column your next
  bomb will travel up — line it up with a ground target's x-position
  before dropping. Bombs are rarer than bullets and only hit **ground
  targets** — the turrets/bunkers scrolling down toward you. A bullet
  does nothing to a ground target, and a bomb does nothing to a plane;
  you have to use the right weapon for the right enemy.
- **Objective:** score as much as you can before you run out of lives —
  enemy planes and ground targets keep spawning forever (an arcade
  score-attack, not a level with an ending). Colliding with an enemy
  plane costs a life and destroys the plane. Running out of lives shows
  "Game Over!" and restarts.

## Project structure

| File | Purpose |
|---|---|
| `project.json` | Project manifest |
| `rooms/room0.json` | The single 480×640 play field |
| `objects/obj_player.json` | The ship — movement, firing/bombing (with cooldowns), the two spawn alarms, the scrolling-background setup, score/lives HUD, and the enemy-plane collision |
| `objects/obj_bullet.json` | Air-to-air weapon — destroys `obj_enemy_plane` on contact (+50) |
| `objects/obj_bomb.json` | Air-to-ground weapon — moves forward (up-screen, negative `vspeed`) to reach a target ahead; destroys `obj_ground_target` on contact (+100) |
| `objects/obj_enemy_plane.json` | Falls toward the player with a little random side-drift; spawned every 40 steps |
| `objects/obj_ground_target.json` | Scrolls down at the same speed as the background, so it reads as fixed to the terrain; spawned every 70 steps |
| `sprites/`, `backgrounds/bg_ground.png` | Original flat-colour art (see `CREDITS.txt`), generated by `tools/gen_sky_strike_1_sprites.py`, including `spr_crosshair.png` (the bombing reticle) |

## Things to tweak

- Fire rate: `obj_player`'s `fire_cooldown` reset value (`8` steps) and
  `bomb_cooldown` (`24` steps), both in the `space`/`z` keyboard handlers.
- Spawn rate: the two `set_alarm` steps counts in `game_start` (`40` for
  planes, `70` for ground targets) and in each alarm handler's own
  re-arm call.
- Scroll speed: `set_background`'s `vspeed` in `game_start` (`2`) — the
  ground targets' own `vspeed` is set to match it in their `create`
  event, so changing one without the other will make targets drift
  relative to the terrain. Bomb speed (`-4`, `obj_bomb`'s `create` event)
  is independent of both — it only has to be negative (forward/up) to
  ever reach a target ahead, and faster (more negative) than the
  target's `+2` to close the gap in reasonable time.
- Enemy plane side-drift: `irandom(2) - 1` in `obj_enemy_plane`'s
  `create` event (currently -1, 0, or 1 px/frame).
- Crosshair position: the fixed forward offset in `obj_player`'s `draw`
  event (`self.y - 89`, i.e. 80px ahead of the ship plus half the
  reticle's own height) — it's a static offset, not a physics-accurate
  landing predictor, matching the classic arcade convention.

## Two real bugs this sample's own authoring hit

- **Spawning fully off-screen self-destructed instantly.** Enemy planes
  and ground targets originally spawned fully above the room (`y = -30`
  for a 24px-tall plane, `y = -40` for a 28px-tall target) — entirely
  outside the room's `0..640` bounds the instant they were created. The
  engine's `outside_room` event fires whenever an instance's sprite is
  **fully** outside the room, which includes the very frame it's created
  on, not just when it flies off during play — so every spawned enemy
  destroyed itself before ever becoming visible, and nothing ever seemed
  to spawn. Fixed by spawning a few pixels *into* the room (`y = -20` /
  `y = -24`) so the sprite always has at least a sliver on-screen at
  creation. Worth remembering for any future sample that spawns
  instances off-screen and relies on `outside_room` to clean them up
  later.
- **The scrolling ground never actually scrolled — a real engine bug,
  not a sample mistake.** `room0.json`'s `"backgrounds"` field was
  copied from another sample's convention: a list of all 8 GMK-style
  background-layer slots, each `visible: false`. The desktop renderer's
  `_render_room` picks the multi-layer path over `set_background`'s own
  legacy single-background scroll whenever that list is simply
  *non-empty* — regardless of whether anything in it is actually
  visible — so `set_background`'s `vspeed` was ticking every frame
  (confirmed correct internally) while nothing ever reached the code
  that draws with it. This is a genuine engine bug (fixed in
  `runtime/game_runner.py`'s `GameRoom._bg_layers_active`, now a live
  check for at least one *visible* layer rather than "list is
  non-empty") — no other bundled sample had tripped it before, since
  this is the first one to actually use `set_background`'s scroll
  feature in a real room. `room0.json` itself was also corrected to the
  room editor's own native default (`"backgrounds": []`), which is what
  a room never touching the multi-layer feature should have.

## Export status

Verified on **desktop** (real `GameRunner` loop, headless, with injected
input exercising movement, firing, bombing, both collision types, and
