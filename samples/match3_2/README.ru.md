# Match-3 — Уровень 2

Продолжение на основе спрайтов и анимации для
[`match3_1`](../match3_1/README.md), обещанное в Дорожной карте того
образца: та же доска и подсчёт очков, теперь нарисованные настоящими
спрайтами самоцветов вместо цветных прямоугольников, с анимацией
сдвига при обмене и звуковыми эффектами для обмена / совпадения /
каскада. По-прежнему одна комната, один объект, без скриптов — вся
игра по-прежнему состоит из четырёх событий `execute_code` на едином
управляющем объекте.

**Куда это вписывается:** часть семьи `match3_*` — чистый скрипт
`execute_code`, без встроенных действий, без плиток на уровне
комнаты. См.
[`../README.md`](../README.md#progression-how-each-family-is-built-not-just-how-it-plays)
о том, чем это отличается от подхода `maze_*`/`plateforme_*` со
встроенными действиями и множеством объектов.

**Звук и музыка:** 3 звуковых файла (`snd_swap`, `snd_match`,
`snd_cascade`), все активно используются — ставятся в очередь из
`execute_code` через `self._sound_queue` (см. ниже), а не действие
`play_sound`.

## Как играть

Так же, как match3_1:

- **Щёлкните** по плитке, чтобы выбрать её (белый контур), затем
  **щёлкните по соседней плитке**, чтобы поменять их местами. Обмен
  теперь **сдвигается** на место вместо мгновенного скачка.
- Если обмен выстраивает **3 или более плиток одинакового цвета** в
  ряд или столбец, совпавшие плитки на мгновение мигают,
  уничтожаются, а плитки над ними **сдвигаются вниз**, чтобы
  заполнить пробел; новые плитки падают сверху доски. Цепные реакции
  ("каскады") разрешаются волнами.
- Обмен, не создающий совпадения, **сдвигается обратно** на исходную
  позицию вместо мгновенного скачка назад.
- Каждая уничтоженная плитка стоит **10 очков**; наберите **500
  очков**, чтобы победить.
- Каждая попытка обмена воспроизводит щелчок; успешное совпадение
  воспроизводит звон, и каждый дополнительный каскад в той же
  комбинации воспроизводит более яркий, восходящий звон.

## Чем отличается от match3_1

| match3_1 | match3_2 |
| -------- | -------- |
| Плитки рисуются как сплошные цветные прямоугольники | Плитки рисуются как **спрайты** самоцветов (команда очереди отрисовки в стиле `draw_sprite`), одна форма на цвет для доступности дальтоникам |
| Обмен применяется мгновенно, совпадения оцениваются немедленно | Обмен сначала **сдвигается** на место (~4 кадра); несовпадающий обмен сдвигается обратно вместо мгновенного скачка |
| Без аудио | **Звуковые эффекты** для обмена / совпадения / каскада, ставятся в очередь из `execute_code` через новый примитив `self._sound_queue` (см. ниже) |

Сама логика доски (модель сетки, поиск совпадений, каскадное
падение, подсчёт очков, условие победы) не изменена по сравнению с
match3_1 — это действительно читаемое отличие, а не переписывание.

## Как работает код

Состояние и конечный автомат `step` такие же, как в match3_1
(`grid`, `sel`, `marked`, `flash`/`flash_total`,
`falling`/`fall_speed`, `score`, `target`, `won`, `find_matches`) —
полное описание см. в README того образца. Новое состояние,
добавленное для этой версии:

| Атрибут | Значение |
| --------- | ------- |
| `sprite_names` | `['spr_gem_red', 'spr_gem_blue', 'spr_gem_green', 'spr_gem_yellow']`, индексировано так же, как был `palette` в match3_1 |
| `swap_off` | словарь `(gx, gy) → (dx, dy)` сдвиг в пикселях для текущего сдвига обмена; спадает до `(0, 0)` со скоростью `swap_speed` px/кадр, та же техника сужения-к-покою, которую `falling` уже использует для каскадов, обобщённая на две оси |
| `swap_phase` | `None` / `'forward'` (сдвиг к обменённой позиции) / `'back'` (отклонённый обмен, сдвигающийся обратно к исходным клеткам) |
| `last_swap` | `(gx, gy, sx, sy)` — две клетки, вовлечённые в обмен в полёте, чтобы `step` мог отменить их без необходимости в состоянии замыкания |
| `pending_marks` | набор совпадений, вычисленный сразу после обмена, удерживается, пока не завершится анимация сдвига, чтобы мигание не началось посреди сдвига |
| `arm_swap(a, b)` | вспомогательная функция (определена в `create`, сохранена на экземпляре, как `find_matches`), которая устанавливает `swap_off` для обеих клеток только из их позиций — повторный вызов с теми же двумя клетками создаёт обратную анимацию, что бесплатно питает сдвиг-отмену |

Обновлённый поток:

```
клик по соседней плитке
  → сетка обменивается немедленно (данные), вычисляются pending_marks
  → swap_off вооружается (forward) — плитки сдвигаются в свои новые клетки
       │
       ▼ (сдвиг оседает)
  pending_marks?
    да → вооружить мигание (мигание → уничтожение → падение → повторное сканирование, как в match3_1)
    нет → сетка обменивается обратно, swap_off вооружается заново с ТЕМИ ЖЕ двумя клетками (phase='back')
             │
             ▼ (сдвиг оседает)
          idle
```

- **`create`** — то же засевание сетки, что и match3_1, плюс
  `sprite_names`, `swap_off`/`swap_speed`/`swap_phase`/`last_swap`/
  `pending_marks`, и вспомогательная функция `arm_swap`.
- **`mouse_left_press`** — логика выбора не изменена; допустимый
  соседний обмен теперь применяет обмен сетки, вычисляет
  `pending_marks`, вооружает сдвиг вперёд и ставит в очередь
  `snd_swap`.
- **`step`** — блоки мигания/падения не изменены по сравнению с
  match3_1 (по-прежнему ставят в очередь `snd_cascade` при цепном
  повторном совпадении); новый блок `elif self.swap_off:` уменьшает
  сдвиг и, когда он осядет, либо вооружает мигание (ставит в очередь
  `snd_match`), либо запускает обратный сдвиг.
- **`draw`** — тот же рисунок панели/доски/выбора/очков/инструкций/
  баннера победы, что и match3_1, но теперь каждая плитка — команда
  очереди отрисовки `{'type': 'sprite', 'sprite_name': ..., 'x':
  ..., 'y': ...}` вместо заполненного прямоугольника (всё ещё
  заменяется на простой белый заполненный прямоугольник во время
  мигания отмеченной плитки, точно как делал match3_1), смещённый на
  `swap_off` в сочетании с `falling`.

### Примитив `self._sound_queue`

`execute_code` имеет живой объект `game` только в среде выполнения
настольного pygame — и экспортированная среда выполнения Kivy, и
среда выполнения Web/Pyodide привязывают `game = None` в этом
контексте, поэтому `game.sounds[...].play()` (очевидный выбор)
работает только на настольном устройстве. Этот образец мотивировал
добавление настоящего кроссплатформенного примитива вместо этого:
любое событие `execute_code` может выполнить

```python
self._sound_queue.append('snd_swap')
# или, для нестандартной громкости:
self._sound_queue.append({'sound': 'snd_swap', 'volume': 0.5})
```

и это воспроизводится одинаково на всех трёх целях:

- **Настольный** — `ActionExecutor.execute_event` опустошает и
  воспроизводит его (через `game.sounds[...]`) сразу после каждого
  события, а не только `draw`.
- **Экспорт Kivy** — `GameObject._drain_sound_queue` (сгенерировано в
  `base_object.py`) разрешает имя через сгенерированный
  `asset_paths.py` (`SOUND_PATHS`) и вызывает имеющийся
  вспомогательный метод `play_sound()`; опустошается раз за кадр на
  живой экземпляр из цикла `update()` сцены, поэтому работает даже
  для объектов без события `draw`.
- **Веб (Pyodide)** — загрузчик Python возвращает любые звуки в
  очереди в JSON-патче рядом с очередью отрисовки; `engine.js`
  воспроизводит их как настоящие элементы `<audio>` через тот же
  путь пула аудио, который уже использует структурированное действие
  `play_sound`.

Тот же пробел в разрешении по имени существовал для команд в стиле
`draw_sprite`, отправленных из сырого `execute_code` (рендеринг
плиток в этом образце) — рендерер очереди отрисовки Kivy раньше
разрешал спрайт только из `sprite_path`, запечённого во время
генерации кода для *структурированных* действий, поэтому вручную
написанный словарь `{'type': 'sprite', 'sprite_name': ...}` там не
рендерился. Исправлено таким же образом: `asset_paths.py` также
несёт `SPRITE_PATHS`, и случай `'sprite'` в очереди отрисовки Kivy
возвращается к нему по имени, когда предварительно разрешённый путь
отсутствует.

### Что можно настроить

Те же рычаги, что и match3_1 (`self.cols`/`self.rows`,
`self.palette`, `self.target`, `flash_total`, `fall_speed`), плюс:

- Скорость анимации обмена: `self.swap_speed` (px/кадр; 24 → ~4
  кадра на сдвиг при `tile=96`).
- Громкость звука: передайте словарь `{'sound': ..., 'volume': ...}`
  вместо голого имени в `self._sound_queue.append(...)`.

## Статус экспорта

- **Test Game (F5) / настольный:** работает — проверено сквозным
  образом с настоящим прогоном `GameRunner`, вставляющим фактический
  клик мыши через стандартный путь событий pygame (обмен → совпадение
  → каскад → очки, с наблюдаемыми фактическими вызовами
  `pygame.mixer.Sound.play()`).
- **Android (.apk) / мобильный (Kivy):** **поддерживается.**
  Проверено, что экспорт компилируется чисто, `asset_paths.py` несёт
  правильные `SPRITE_PATHS`/`SOUND_PATHS`, а изображения спрайтов /
  звуковые файлы копируются в `assets/images` / `assets/sounds`. Для
  фактической сборки `.apk` дополнительно требуется buildozer (через
  WSL на Windows) — см. [`docs/ANDROID_EXPORT.md`](../../docs/ANDROID_EXPORT.md).
- **Веб (HTML5):** **поддерживается.** Загрузчик Pyodide
  экспортированной страницы опустошает `self._sound_queue` в тот же
  JSON-обмен, что и очередь отрисовки; проверено, что сгенерированный
  загрузчик компилируется и правильно передаёт туда-обратно как
  команды отрисовки, так и поставленные в очередь звуки под чистым
  CPython (для этой проверки браузер не нужен — сам запуск Pyodide в
  браузере не проверяется автоматизированной сборкой, та же оговорка,
  что и в match3_1). Требует доступа в интернет при первой загрузке
  (Pyodide загружается из CDN).
- **Автономный zip:** не проверено с этим образцом.
