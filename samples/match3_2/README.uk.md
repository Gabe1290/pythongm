# Match-3 — Рівень 2

Продовження на основі спрайтів і анімацій для
[`match3_1`](../match3_1/README.md), обіцяне в Дорожній карті того
зразка: та сама дошка та підрахунок очок, тепер намальовані
справжніми спрайтами самоцвітів замість кольорових прямокутників, з
анімацією зсуву при обміні та звуковими ефектами для обміну /
збігу / каскаду. Досі одна кімната, один об'єкт, без скриптів — уся
гра досі складається з чотирьох подій `execute_code` на єдиному
контрольному об'єкті.

**Куди це вписується:** частина родини `match3_*` — чистий скрипт
`execute_code`, без вбудованих дій, без плиток на рівні кімнати. Див.
[`../README.md`](../README.md#progression-how-each-family-is-built-not-just-how-it-plays)
про те, як це відрізняється від підходу `maze_*`/`plateforme_*` з
вбудованими діями та багатьма об'єктами.

**Звук і музика:** 3 звукові файли (`snd_swap`, `snd_match`,
`snd_cascade`), усі активно використовуються — ставляться в чергу з
`execute_code` через `self._sound_queue` (див. нижче), а не дію
`play_sound`.

## Як грати

Так само, як match3_1:

- **Клацніть** плитку, щоб вибрати її (білий контур), потім
  **клацніть сусідню плитку**, щоб поміняти їх місцями. Обмін тепер
  **зсувається** на місце замість миттєвого стрибка.
- Якщо обмін вирівнює **3 або більше плиток однакового кольору** в
  ряд або стовпець, збіжні плитки на мить блимають, знищуються, а
  плитки над ними **зсуваються вниз**, щоб заповнити прогалину; нові
  плитки падають зверху дошки. Ланцюгові реакції ("каскади")
  розв'язуються хвилями.
- Обмін, що не створює збігу, **зсувається назад** до початкової
  позиції замість миттєвого стрибка назад.
- Кожна знищена плитка коштує **10 очок**; досягніть **500 очок**,
  щоб перемогти.
- Кожна спроба обміну відтворює клацання; успішний збіг відтворює
  дзвін, і кожен додатковий каскад у тій самій комбінації відтворює
  яскравіший, висхідний дзвін.

## Чим відрізняється від match3_1

| match3_1 | match3_2 |
| -------- | -------- |
| Плитки намальовані як суцільні кольорові прямокутники | Плитки намальовані як **спрайти** самоцвітів (команда черги малювання в стилі `draw_sprite`), одна форма на колір для доступності для дальтоніків |
| Обмін застосовується миттєво, збіги оцінюються негайно | Обмін спочатку **зсувається** на місце (~4 кадри); обмін без збігу зсувається назад замість миттєвого стрибка |
| Без аудіо | **Звукові ефекти** для обміну / збігу / каскаду, ставляться в чергу з `execute_code` через новий примітив `self._sound_queue` (див. нижче) |

Сама логіка дошки (модель сітки, пошук збігів, каскадне падіння,
підрахунок очок, умова перемоги) не змінена порівняно з match3_1 — це
справді читабельна різниця, а не переписування.

## Як працює код

Стан і скінченний автомат `step` такі самі, як у match3_1 (`grid`,
`sel`, `marked`, `flash`/`flash_total`, `falling`/`fall_speed`,
`score`, `target`, `won`, `find_matches`) — повний опис див. у README
того зразка. Новий стан, доданий для цієї версії:

| Атрибут | Значення |
| --------- | ------- |
| `sprite_names` | `['spr_gem_red', 'spr_gem_blue', 'spr_gem_green', 'spr_gem_yellow']`, індексовано так само, як був `palette` у match3_1 |
| `swap_off` | словник `(gx, gy) → (dx, dy)` зсув у пікселях для зсуву обміну, що триває; спадає до `(0, 0)` зі швидкістю `swap_speed` px/кадр, та сама техніка звуження-до-спокою, яку `falling` вже використовує для каскадів, узагальнена на дві осі |
| `swap_phase` | `None` / `'forward'` (зсув до обміняної позиції) / `'back'` (відхилений обмін, що зсувається назад до початкових клітинок) |
| `last_swap` | `(gx, gy, sx, sy)` — дві клітинки, залучені до обміну в польоті, щоб `step` міг скасувати їх без потреби у стані замикання |
| `pending_marks` | набір збігів, обчислений одразу після обміну, утримується, поки не завершиться анімація зсуву, щоб блимання не почалося посеред зсуву |
| `arm_swap(a, b)` | допоміжна функція (визначена в `create`, збережена на екземплярі, як `find_matches`), що встановлює `swap_off` для обох клітинок лише з їхніх позицій — повторний виклик з тими самими двома клітинками створює зворотну анімацію, що безкоштовно живить зсув-скасування |

Оновлений потік:

```
клацання по сусідній плитці
  → сітка обмінюється негайно (дані), обчислюються pending_marks
  → swap_off озброюється (forward) — плитки зсуваються у свої нові клітинки
       │
       ▼ (зсув осідає)
  pending_marks?
    так → озброїти блимання (блимання → знищення → падіння → повторне сканування, як у match3_1)
    ні  → сітка обмінюється назад, swap_off озброюється повторно з ТИМИ САМИМИ двома клітинками (phase='back')
             │
             ▼ (зсув осідає)
          idle
```

- **`create`** — те саме засівання сітки, що й match3_1, плюс
  `sprite_names`, `swap_off`/`swap_speed`/`swap_phase`/`last_swap`/
  `pending_marks`, і допоміжна функція `arm_swap`.
- **`mouse_left_press`** — логіка вибору не змінена; дійсний сусідній
  обмін тепер застосовує обмін сітки, обчислює `pending_marks`,
  озброює зсув уперед і ставить у чергу `snd_swap`.
- **`step`** — блоки блимання/падіння не змінені порівняно з match3_1
  (усе ще ставлять у чергу `snd_cascade` при ланцюговому повторному
  збігу); новий блок `elif self.swap_off:` спадає зсув і, коли осяде,
  або озброює блимання (ставить у чергу `snd_match`), або запускає
  зворотний зсув.
- **`draw`** — той самий малюнок панелі/дошки/вибору/очок/
  інструкцій/банера перемоги, що й match3_1, але тепер кожна плитка —
  команда черги малювання `{'type': 'sprite', 'sprite_name': ...,
  'x': ..., 'y': ...}` замість заповненого прямокутника (усе ще
  замінюється на простий білий заповнений прямокутник під час
  блимання позначеної плитки, точно як робив match3_1), зсунута на
  `swap_off` у поєднанні з `falling`.

### Примітив `self._sound_queue`

`execute_code` має живий об'єкт `game` лише в середовищі виконання
настільного pygame — і експортоване середовище виконання Kivy, і
середовище виконання Web/Pyodide прив'язують `game = None` в цьому
контексті, тому `game.sounds[...].play()` (очевидний вибір) працює
лише на настільному пристрої. Цей зразок мотивував додавання
справжнього кросплатформового примітиву замість цього: будь-яка подія
`execute_code` може виконати

```python
self._sound_queue.append('snd_swap')
# або, для нестандартної гучності:
self._sound_queue.append({'sound': 'snd_swap', 'volume': 0.5})
```

і це відтворюється однаково на всіх трьох цілях:

- **Настільний** — `ActionExecutor.execute_event` спорожняє й
  відтворює його (через `game.sounds[...]`) одразу після кожної
  події, а не лише `draw`.
- **Експорт Kivy** — `GameObject._drain_sound_queue` (згенеровано в
  `base_object.py`) розв'язує ім'я через згенерований `asset_paths.py`
  (`SOUND_PATHS`) і викликає наявний допоміжний засіб `play_sound()`;
  спорожняється раз за кадр на живий екземпляр з циклу `update()`
  сцени, тому працює навіть для об'єктів без події `draw`.
- **Веб (Pyodide)** — завантажувач Python повертає будь-які звуки в
  черзі в JSON-патчі поряд із чергою малювання; `engine.js`
  відтворює їх як справжні елементи `<audio>` через той самий шлях
  пулу аудіо, який вже використовує структурована дія `play_sound`.

Той самий пропуск у розв'язанні за іменем існував для команд у стилі
`draw_sprite`, надісланих із сирого `execute_code` (рендеринг плиток
у цьому зразку) — рендерер черги малювання Kivy раніше розв'язував
спрайт лише з `sprite_path`, запеченого під час генерації коду для
*структурованих* дій, тому вручну написаний словник `{'type':
'sprite', 'sprite_name': ...}` там не рендерився. Виправлено таким
самим чином: `asset_paths.py` також несе `SPRITE_PATHS`, і випадок
`'sprite'` у черзі малювання Kivy повертається до нього за іменем,
коли попередньо розв'язаний шлях відсутній.

### Що можна налаштувати

Ті самі важелі, що й match3_1 (`self.cols`/`self.rows`,
`self.palette`, `self.target`, `flash_total`, `fall_speed`), плюс:

- Швидкість анімації обміну: `self.swap_speed` (px/кадр; 24 → ~4
  кадри на зсув при `tile=96`).
- Гучність звуку: передайте словник `{'sound': ..., 'volume': ...}`
  замість голого імені в `self._sound_queue.append(...)`.

## Статус експорту

- **Test Game (F5) / настільний:** працює — перевірено наскрізно за
  допомогою справжнього прогону `GameRunner`, що вставляє фактичне
  клацання миші через стандартний шлях подій pygame (обмін → збіг →
  каскад → очки, зі спостережуваними фактичними викликами
  `pygame.mixer.Sound.play()`).
- **Android (.apk) / мобільний (Kivy):** **підтримується.** Перевірено,
  що експорт компілюється чисто, `asset_paths.py` несе правильні
  `SPRITE_PATHS`/`SOUND_PATHS`, а зображення спрайтів / звукові файли
  копіюються в `assets/images` / `assets/sounds`. Для фактичної
  збірки `.apk` додатково потрібен buildozer (через WSL на Windows) —
  див. [`docs/ANDROID_EXPORT.md`](../../docs/ANDROID_EXPORT.md).
- **Веб (HTML5):** **підтримується.** Завантажувач Pyodide
  експортованої сторінки спорожняє `self._sound_queue` в той самий
  JSON-обмін, що й чергу малювання; перевірено, що згенерований
  завантажувач компілюється й правильно передає туди-назад як команди
  малювання, так і поставлені в чергу звуки під чистим CPython (для
  цієї перевірки браузер не потрібен — сам запуск Pyodide в браузері
  не перевіряється автоматизованою збіркою, те саме застереження, що
  й у match3_1). Потребує доступу до інтернету при першому
  завантаженні (Pyodide завантажується з CDN).
- **Автономний zip:** не перевірено з цим зразком.
