# Open work — a queue to work through one item at a time

Written 2026-10-29, at the end of the micro:bit Stage P / wiki session. This is
the resume state: tick a box (and add the commit hash) when an item is done, one
item per commit, push after each. Work **top to bottom**: part A needs nobody
else, part B needs an explicit yes from the owner, part C needs hardware or a
person and cannot be finished from a terminal. The wider map is
`docs/PROJECT_STATUS.md`; `TODO.md` holds the smaller feature-level items.

Conventions that apply to every item: French and the other accented languages
keep their accents; commit and push straight to `main`; verify a claim in code
before writing it down; a new test is mutation-checked; test paths are anchored
to the test file (CI runs pytest from `tests/`).

    `Qt6Quick.dll + 0x11593b` every time, `Qt6WebEngineWidgets`/`Qt6QuickWidgets`
    and shiboken frames on the stack: the crash is inside the `QWebEngineView`'s own
    QQuickWidget. Each Qt WebEngine view is an in-process Chromium page.
  - Forcing software rendering (`QT_QUICK_BACKEND=software`) is **not** a fix: the
    default path never initialises Qt Quick's scene graph for an unshown view, and
    the setting only makes Chromium log GL-context errors.

    called `widget.deleteLater()` on four widgets that each own a WebEngine view and
    never ran the deferred delete; the round-trip fixture's view was freed by
    refcounting the instant the fixture returned. Both now go through
    `conftest.dispose_qt_widget`, which closes the widget and runs the deletion.
    **Unproven**: with no reproduction there is no before/after rate.
  - `tools/analyze_crash_dump.py` names the faulting DLL, offset and caller chain
    of a `python.exe` dump in seconds. *If it crashes again:* run it on the newest
    dump in `%LOCALAPPDATA%\CrashDumps`; the same `Qt6Quick.dll + 0x11593b` means
    the same bug, a different spot means the hardening moved it.
  - *Done when:* the full suite has run green five times in a row after the next
    day or two of normal use, or a dump shows a different cause.
  - *Recurrence 2026-10-30:* the first full run of the day died in the same place
    (`test_blockly_block_audit_roundtrip.py` line 749 = `app.exec()` inside the module-scoped
    `round_tripped` fixture, i.e. on the main thread while Chromium loads the page); the immediate
    rerun passed (8,045). No dump was written (pytest's faulthandler plugin handles the exception
    first, so Windows never sees it). Checked and ruled out: `AA_ShareOpenGLContexts` is False in
    both import orders but a lone view loads fine either way with no Qt warning; 6 more runs of the
    1,547 tests before the crash point, with `-p no:faulthandler` so WER can dump, all passed.
