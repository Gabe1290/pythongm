# micro:bit Stage P -- export parity (HTML5 + Kivy)

Parent: `docs/MICROBIT_EXTENSION_PLAN.md` ("Stage P -- export parity (sketch)").
Goal: a project using the simulated micro:bit plays the same in an HTML5 export
and a Kivy (Android/iOS) export as in the IDE. Today both targets skip the 16
micro:bit actions (a warning) and the Kivy generator **drops the 24 events
silently**. Desktop export needs nothing: it freezes the real engine and the
extension rides along.

Rules (CLAUDE.md): one unit = one commit + a regression test + the full suite;
commit and push after each; this file's checkboxes are the resume state.

## What exists to build on

| | HTML5 | Kivy |
|---|---|---|
| Extension seam | `export_html5.js`, concatenated at `__PYGM_EXTENSION_JS__`; `registerExtensionAction`, `registerFrameUpdate`, `registerRoomRenderer` | `export_kivy.py`: `SCENE_CODE`, `BASE_OBJECT_CODE`, `ACTION_CODEGEN` |
| Simulator | **must be rewritten in JS** (558 lines + font/images/melodies/radio tables) | **reuse `simulator.py` verbatim** -- it is pure Python (imports only `font`, `images`, `sound`, `radio`); embed the five modules into the export |
| Gaps in the seams | no per-instance overlay hook, no mouse/key input hook | no event-name hook, no input/overlay hook |
| Verification | no Node in CI; **Playwright + Chromium are installed on the dev box** -> real JS parity run locally, structural/golden tests in CI | stub-Kivy harness (`test_kivy_raycast.py` pattern) + generated-file compile |

Design decision: **the simulator is ported, not re-specified.** The Python
`MicrobitSimulator` is the oracle. For JS, a local-only parity tool drives the
Python and JS simulators with the same scripted input and diffs display, tone,
gesture and the reported event list frame by frame. A recorded golden trace
(generated from Python, committed) is checked in CI against structural
properties of the JS (constants and tables equal to the Python source).

## Units

### P0 -- Kivy must not drop events silently
- [x] The Kivy generator warns once per unknown event name (generic, not
  micro:bit-specific), like it already does for actions. Test with a project
  that authors `microbit_button_a`.

### HTML5
- [x] **H1 -- JS simulator.** `extensions/microbit/export_html5.js`:
  tables (font, images, melody parser, radio helpers) and `MicrobitSimulator`
  with the same API/report tuples. Local parity tool
  `tools/microbit_js_parity.py` (Playwright) + CI test that pins the JS
  constants/tables to the Python source. *Done:* 60 seeds x 500 random calls
  identical in Chromium; tables generated by `tools/gen_microbit_js_tables.py`
  (glyphs keyed by char code -- the brace-balance guard can't read quotes).
- [x] **H2 -- actions, conditions, events.** 16 `registerExtensionAction`s
  (read_sensor, if_button/gesture/tilt/pixel return bool the way engine.js
  conditions do); frame update steps every board and fires the reported events
  (`event_name_for` table); radio delivery per room; board detection
  (`microbit*` name / `is_microbit`). Needs engine.js to expose the bool-result
  contract for extension conditions -- check first.
  *Done:* two generic engine.js seams -- `registerExtensionCondition` (a
  registered name is a question: it gates the next action and picks then/else;
  `isConditionalAction`/`evaluateCondition` consult it) and
  `GameObject.instanceData` (the room entry, for `is_microbit`). Extension side:
  12 actions + 4 conditions, `updateMicrobits` (radio delivery, simulator step,
  events through the generated `MB_EVENT_FIXED`/`MB_GESTURE_EVENTS` tables).
  Verified by exporting `microbit_1` and driving the real engine in Chromium
  (`tests/test_microbit_html5_actions.py`, dev box only; four mutations caught).
  Differences from desktop, stated plainly: events fire at the START of the
  frame (the HTML5 hook runs before the room steps; desktop runs it after
  collisions), and the step is `1 / roomSpeed` per rendered frame, like the
  rest of the HTML5 engine. Sound reports are delivered to `soundHooks` (H5).
- [x] **H3 -- drawing.** New generic engine.js seam
  `registerInstanceOverlay(fn(inst, ctx))` (mirror of desktop's
  `PLUGIN_INSTANCE_OVERLAYS`), then layout + board + sensor strip in canvas 2D.
  Assert WHERE LEDs/buttons land (pixel samples at layout coordinates), not
  that something drew.
  *Done:* engine.js `registerInstanceOverlay` / `runInstanceOverlays`, called
  after the room renders on all three paths (2.5D, no views, views), like the
  desktop hook. Layout, board and sensor strip ported to canvas 2D. Python's
  round-half-to-even is reproduced (`pyRound`): Math.round differs on exact
  halves and the layout is integer-snapped. Verified in Chromium: layout fuzz
  vs `layout.py` (300 positions x scales incl. exact halves), and the canvas
  vs pygame colour at 60+ points per state (every LED, button, pad, logo,
  speaker, tilt dot, slider knob; 7 states x 2 placements), plus a real export
  of `microbit_1` painting the board where `layoutFor` says. Text labels use
  a CSS font (not pygame's), so glyph shapes differ slightly; positions match.
- [x] **H4 -- input.** Generic seam for pointer/key hooks; mouse (left/right,
  chord), strip drag (tilt, sliders), opt-in keyboard. Touch-screen friendly
  (pointer events).
  *Done:* engine.js `registerInputHandler` / `runInputHandlers` (mirror of the
  desktop `register_input_handler`): mouse and touch go through it before the
  authored mouse events (a handler returning true swallows the click), key
  hooks run per instance and never swallow, `game.pointer` tracks the pointer,
  and a window-level release ends a press that began on the canvas. Extension:
  `hitTest`/`stripHitTest`/`tiltFromPos`/`sliderFromX` (fuzz-compared with
  `layout.py`: 2,500 points, no differences), left press, the right-click A+B
  chord, strip drags that follow the pointer each frame, tilt spring-back, and
  the opt-in keyboard (A/B/S/arrows). Verified in Chromium with real mouse,
  touch and key events against an export of `microbit_1`
  (`tests/test_microbit_html5_input.py`, dev box only; 8 breakages caught).
  Multi-touch isn't handled (the first touch only), as in the engine itself.

- [x] **H5 -- sound.** WebAudio square wave from `sound_note` / `sound_stop`
  reports; resume the context on first user gesture.
  *Done:* `makeSpeaker` (one voice, a new note replaces it, rests and `sound_stop` cut it off,
  gain/length cap equal audio.py's, injectable context so it is tested with a recording fake),
  `soundHooks` wired to it, context resumed on the first pointer/key/touch.
  *Not checked:* actual loudness/timbre by ear on a real device (same open item as desktop).
- [x] **H6 -- close-out.** Real-browser playtest of `microbit_1` via Playwright
  (screenshot compared with the pygame frame), README/wiki/CLAUDE.md note.
  *Done:* `tests/test_microbit_html5_playtest.py` renders the same project in
  the pygame engine and in the HTML5 export (headless Chromium) and compares
  the frames: under 3% of the board/strip area differs (anti-aliased edges
  only), and solid colours at 7 sample points are identical. **It found a real
  pre-existing HTML5 bug:** `draw_text` ignored its `color` param (desktop had
  the same bug, fixed 2026-09-04), so every sample's authored text colour was
  lost on HTML5 -- white help text drew black on the dark room. Fixed in
  engine.js. README, wiki Microbit (EN + FR) updated; HTML5 is done, Kivy
  (K1-K6) is next.

### Kivy
- [x] **K1 -- embed the pure modules + actions.** Copy `simulator.py`, `font`,
  `images`, `sound`, `radio`, `events` into the export; `ACTION_CODEGEN` for
  the 16 actions calling a `_mb_*` helper on `GameObject` (M34 two-halves
  pattern: codegen emits calls, helpers hold the logic).
  *Done:* two generic Kivy-export seams -- `SUPPORT_FILES` (an extension's
  files copied byte for byte into `game/`, path-escape guarded) and
  `CONDITION_CODEGEN` (an extension's question action -> a boolean expression
  the generator wraps in its normal guard). `extensions/microbit/export_kivy.py`:
  the simulator ships as the `microbit_sim` package (simulator, font, images,
  sound, melodies, radio -- `events.py`/`layout.py` are not needed yet);
  12 action + 4 condition codegens emit calls to `_mb_*` helpers injected into
  the base object. `tests/test_kivy_microbit_actions.py` imports the real
  generated object under a stub kivy and compares what each action/condition
  does with what the desktop handler does (same params), plus byte-identity of
  the shipped simulator. Boards are recognised by object name (`microbit*`) or
  an `is_microbit` attribute; the flag form on an object property is wired in
  K2 with the events. Events are still skipped (warned) until K2.
- [x] **K2 -- events + frame update.** Done. New generic Kivy seams: an
  extension's `export_kivy.py` may expose `EVENT_METHODS` ({event type: handler
  name}; the generator emits the method instead of skipping the event) and the
  scene calls `_update_extensions(dt)` after collision, before end step (the
  desktop's `after_collision`). The microbit `SCENE_CODE` overrides it: radio
  delivery, `sim.update(min(dt, 0.1))`, `radio_string`/`radio_number`, then
  `on_<event>()` on the board. The event tables are repeated as data in
  `export_kivy.py` and pinned to `events.py` by
  `tests/test_kivy_microbit_events.py` (which also drives the real generated
  scene and compares fired events with the desktop mapping). Not done: the
  `is_microbit` flag from a room entry (done later, queue item A6: `INSTANCE_ATTRS`);
  sound reports are ignored until K5; `_update_extensions` was a single override (made a dispatcher, queue item A8).
- [x] **K3 -- drawing.** Done, by a different route than sketched: the board is
  built as **draw-queue commands** (`kivy_draw.py` -> `microbit_sim/draw.py`;
  `layout.py` ships verbatim with a stub `state.py`) and drawn by the exported
  game's own `_dq_render_cmd` into a per-board group on the instance's
  `canvas.after`, so the y-flip and view handling already exist. The queue has
  no polygon or rounded rectangle, so the corner wedge, A/B tags and rounded
  corners are left out. Text gained an optional `anchor` (center / midbottom /
  bottomleft) in the Kivy renderer. `tests/test_kivy_microbit_draw.py`
  rasterises the commands and compares ~40 sample points per state with
  `renderer.py` (10 states x 2 scales). Unverified: a real Kivy canvas, text size
  (one fixed font, scaled), boards inside a views room. Scale, the strip
  toggle and the keyboard opt-in are read from instance variables or the object's
  properties (baked in by `OBJECT_ATTRS`, queue item A7).
- [x] **K4 -- input.** Done. `kivy_touch.py` -> `microbit_sim/touch.py` mirrors
  `input.py` (presses, the A+B right-click chord, tilt pad and slider drags, the
  opt-in keyboard) but takes the geometry explicitly. New generic Kivy scene
  hooks: `_extension_touch_down/up/move` (True swallows, so no authored mouse
  event fires) and `_extension_key_down/up`; the scene gained `on_touch_move`.
  Touches use room coordinates (the space the board is drawn in); keycodes map
  a/b/s and the arrows; the keyboard is the `microbit_keyboard` instance
  variable. `tests/test_kivy_microbit_touch.py` drives `input.py` and the Kivy
  module with the same ~40 gestures and 11 key runs and compares the simulator
  state. Not verified: a real touch screen; a tilt drag keeps the strip
  geometry from when it started if the board moves mid-drag.
- [x] **K5 -- sound.** Done. `kivy_audio.py` -> `microbit_sim/speaker.py`: a note is
  rendered to a mono 22.05 kHz WAV (same square wave, loudness and 10 s cap as
  `audio.py`; samples pinned equal to `audio.square_wave`) in a temp folder
  (bounded, removed at exit) and played with `SoundLoader`; one voice, a new
  note or `sound_stop` cuts the old one; no audio device is survivable. The
  scene routes the simulator's `sound_note`/`sound_stop` reports to it. Not
  verified: that it is audible on a real device, and the loudness (the same
  guess as the desktop).
- [x] **K6 -- close-out.** Done. `tests/test_kivy_microbit_e2e.py` exports the real
  `microbit_1` sample, compiles every generated file, checks no micro:bit event
  or action is dropped, and plays it under the stub kivy (Create, buttons A/B,
  the A+B chord, a shake that rolls the die, the logo scroll, the opt-in
  keyboard, drawing) against twin simulators. Wiki Microbit pages (EN/FR),
  README and TODO updated. **Needs human eyes:** a real Android/iOS run - touch,
  the drawn look and text size, audibility of the beep.
