# What we can do now — plan, 2026-09-06

Written after `docs/POST_1_0_REFACTOR.md` closed (all four file splits plus the
`action_handlers` teardown). Every large initiative in `docs/PROJECT_STATUS.md`
is now either finished or blocked on hardware, so this plan exists to answer
one question: **what is actually workable today.**

**The blocking constraint:** LAN multiplayer cannot be tested (it needs two
machines on a school LAN), there is no Android device to hand, and no Mac. So
everything below either needs no hardware at all, or needs only this Windows
box and a browser.

Same discipline as the refactor: one unit per commit, pushed immediately, full
suite as the gate, so a mid-session stop loses nothing.

## Track A — code work, no hardware needed

### A1. Extension action names are untranslated — DONE 2026-09-06

Shipped in three commits (`665ea14a`, `9c1855a6`, `407ba076`). All 37 actions
contributed by plugins and folder extensions now resolve in all ten shipped
languages, in both Qt contexts.

- [x] **A1.1** Source-language rule: extension actions are authored in
      **English** and localized through the catalogues, like the rest of the
      codebase. *Prerequisite found while scoping and fixed first:* action
      descriptions and parameter tooltips were displayed with a bare `QLabel`,
      never `tr()`, so **no description in the app could be translated at
      all** — zero appear in any catalogue because there was nothing for
      `lrelease` to collect. Without fixing that, re-authoring the multiplayer
      extension would have handed French teachers English descriptions.
- [x] **A1.2** `extensions/multiplayer_lan` re-authored in English — 97
      strings across 15 actions, 6 events, their descriptions and 31 parameter
      labels, plus the `Réseau` → `Network` category — with every French
      string added to `pygm2_fr.ts` **in the same commit**, so French users
      lost nothing at any point in the history.
- [x] **A1.3** All 37 names translated into de/es/fr/it/ja/pt/ru/sl/uk/zh.
- [x] **A1.4** `tests/test_extension_action_i18n.py`: every name resolves in
      every language, driven through the real `LanguageManager`.

**Scope correction worth keeping.** The count is **37, not 35**: `check_sound`
and `stop_sound` sit in the Audio category but are declared statically in core,
so "what did `load_all_plugins` add?" misses them. Filtering by *category* is
what the user actually sees in the palette.

**Still open, and bigger than A1 was:** action *descriptions* and *parameter
labels* remain untranslated — 279 distinct strings, ~2,790 translations. That
gap affects **core** actions equally, so it is not extension work; it now has
somewhere to go, since those strings are finally `tr()`-wrapped.

**Landmines this pass hit, all now guarded:** a `type="vanished"` entry is
dropped by `lrelease`, so three audio actions carried correct translations that
never reached a user; appending a live duplicate beside a vanished one does not
resolve either (two messages, one source, one context) — they must be
un-vanished in place; and a module-scoped translator fixture let French mask a
missing German string, then leaked French into ten unrelated widget tests.

### A3. Block World renders far below its own target frame rate

Measured 2026-08-21: `block_world_1` ~9.6 fps and `block_world_2` ~3.85 fps
against a project-configured 30 fps. Movement is correct; the renderer cannot
keep up. The occlusion-culling pass helped `block_world_1` about 20% and made
`block_world_2` about 12% *worse*.

Fully measurable headlessly, no hardware. It was deliberately parked once in
favour of `sky_strike_1`, so picking it up should be a decision rather than an
assumption.

- [x] **A3.1** Re-measured 2026-09-06. Harness committed as
      `tools/measure_block_world_fps.py`. **Two corrections to the framing
      above:**

      *The renderer has not changed since August.* This item's premise was
      that it had; `git diff 25983640 HEAD -- extensions/block_world samples/
      block_world_*` is empty. The August figures came from a **different,
      slower machine** — at that exact commit, via a worktree, this Windows
      box gives ~19.1 / ~8.1 fps for the same samples. The August trade-off
      does reproduce here (16.4 → 19.1, +17%; 9.1 → 8.1, −11%), so the numbers
      were sound, just not portable. **An fps number is only comparable to one
      taken on the same machine.**

      *One number per sample was hiding the worst case.* Where the camera
      stands matters more than which sample it is: `block_world_1` runs at
      **19.3 fps standing still and 3.8 fps walking** — 7.8× under target,
      exactly when the player is moving. `block_world_2` is flat at ~8.2.

      | | static | walking |
      |---|---|---|
      | `block_world_1` | 19.3 fps | **3.8 fps** |
      | `block_world_2` | 8.2 fps | 8.2 fps |

- [x] **A3.2** Profiled 2026-09-06 (`tools/measure_block_world_fps.py
      --profile`, cProfile by tottime). The two cost regimes A3.1 predicted
      are real, and each has one named culprit.

      **Walking (`block_world_1`, the 3.8 fps case): 48.9% of the frame is a
      single `Surface.fill`.** It is `renderer.py:706` —
      `_draw_wall_strip` scales a 1px-wide texture column up to the strip
      height and *then* applies distance shading with a per-pixel
      `BLEND_RGB_MULT` over the whole scaled strip. Walk up to a wall and
      those strips are full-screen height, so the shading pass alone touches
      **23.5M pixels/frame**. Shading the 1px *source* column instead would
      touch 319K — a measured **73.7× reduction**, and `transform.scale`
      (14.2%) sits right behind it.

      **Standing in open terrain (`block_world_2`, flat ~8.2 fps): death by a
      thousand cuts, no single hot spot.** `_draw_wall_strip` 21.5% over
      18,023 calls/frame, `render_block_world_view` 12.4%, and — worth its own
      line — **`min()` and `max()` together are 10.6%** across *272,000 calls
      per frame*, about 7.5 clamp calls per wall strip. Then `_texel` 4.4%,
      `fill` 4.3%, `scale` 4.0%, `blit` 3.4%, `subsurface` 3.0%. This regime is
      Python-level per-column overhead, so it needs fewer, wider operations
      rather than a cheaper one.

      **The first optimisation is already proven safe.** Shading the source
      column instead of the scaled strip is only valid if a per-pixel multiply
      commutes with `transform.scale` — true if and only if that scale is a
      nearest-neighbour copy. Checked, not assumed: **byte-identical output
      across 2,464 combinations** of source height, destination height, strip
      width and shade value. (`smoothscale` would *not* commute; this rests on
      `scale` specifically.)
- [ ] **A3.3** One optimisation per commit, each with a before/after fps
      number in the commit body — from `tools/measure_block_world_fps.py`, on
      one machine, both camera conditions.
      - [x] **Unit 1 — shade the source column** (the walking regime).
            `block_world_1` walking **3.45 → 12.00 fps (3.4×)**, worst frame
            **390 ms → 106 ms**; the other three conditions flat within ±1.5%;
            output pixel-identical across 16 scripted camera paths × 26 frames.
            A cost threshold picks the branch per strip — shading at source
            unconditionally was 8% *slower* on `block_world_2`, because a
            distant block's strip is a few pixels tall and the Surface copy
            costs more than it saves.
      - [x] **Unit 2a — hoist the per-column clamps** (invisible). min/max
            were 10.6% of a frame across ~272k calls; conditionals instead.
            **+10% on every case**, pixel-identical.
      - [x] **Unit 2b — `DEFAULT_COLUMNS` 320 → 160** (visible, and
            authorised: *"we could make the textures a bit more pixelated if
            that improves the speed"*). Cost is per column, so halving them
            nearly doubles the rate: `block_world_1` static **18.80 → 34.17 fps
            — the 30 fps target is met** — walking 11.80 → 16.80;
            `block_world_2` **8.10 → 14.92** and 8.15 → 15.04. 4px strips
            instead of 2px on a 640px window; with 16px block textures only the
            diagonal block edges get chunkier. Six copies of the number existed
            across the three renderers — desktop now shares
            `state.DEFAULT_COLUMNS` and a test pins all three, so an export
            cannot drift from Test Game.
      - [x] **Unit 2c — merging adjacent columns is dead, and measured
            dead before it was built.** Mean run of identical adjacent columns
            is **1.05–1.12**: each column has its own distance, so its own
            strip height and shade, and almost none match their neighbour.
            The merge machinery would add per-column bookkeeping to collapse
            ~5% of strips — the same trade that made occlusion culling a net
            loss on open terrain. Shipped in its place: shaving the per-strip
            path (`screen.get_height()` ran ~20,600×/frame for a value the
            caller had; `_has_neighbor` was a call twice per strip; the shade
            helpers got 2a's treatment) — **~+5%**, pixel-identical.

      **Cumulative across A3.3, same machine:** `block_world_1` static
      **17.31 → 35.88 (2.1×, and past its 30 fps target)**, walking **3.45 →
      16.53 (4.8×)**; `block_world_2` 7.43 → 15.69 and 7.40 → 15.69 (2.1×
      each).

      **Followed by `docs/BLOCK_WORLD_PERF_PLAN.md` Phase 1 (2026-09-07): distance
fog + a shorter render distance took `block_world_2` a further +69%/+78% on
desktop. The export ports are that plan's open item.**

**A3 is finished as a micro-optimisation exercise.** Every lead in the
      A3.2 profile has been shipped or measured and rejected. `block_world_2`
      remains 1.9× under target, and closing that needs a *different*
      rendering approach — numpy-vectorised column compositing, or batching a
      frame into one surface op — which is a new plan, not a continuation of
      this one.

**Harness landmine, cost a wrong number before it was caught:** the first
version held the **Up arrow** as its "moving" condition. In these samples
Up/Down are bound to `set_look_pitch` (+2°/frame, relative), not to movement —
so it tilted the camera at the empty sky and measured a 3× "speedup" that was
a blank screen. W is what walks. Pinned by
`tests/test_block_world_fps_harness.py`, which also fails if a sample rebinds
those keys. A second lesson from the same pass: the *identical* static
condition measured ~14 fps and ~24 fps minutes apart from background load
alone, so the harness interleaves conditions and prints the full spread.

### A4. Kivy could not resolve `global.X` — DONE 2026-09-06

Filed as "display-only": `draw_text` showing the literal text
`global.team_score`. Reading the code before choosing found it was three
failures of one documented feature (Set Variable's own description says
"instance or **global** variable"), and the worst was not the cosmetic one:

| | desktop | HTML5 | Kivy, before |
|---|---|---|---|
| `set_variable` on `global.X` | ✅ | ✅ | **`self.global.coins = 5` — a SyntaxError, which per the Phase 7.3 note takes the whole generated module's import with it** |
| condition on `global.X` | ✅ | ✅ | silently substituted with `0` |
| `draw_text` `global.X` | ✅ | ✅ (narrow `^global\.(\w+)$`) | drawn as literal characters |

**Decision taken: build the store** (option B of the three offered). `GameApp`
now keeps `self.globals` beside `score`/`lives`, reached from generated code
through main.py's `get_global`/`set_global` — the same call-time
`__import__('main')` pattern `_EXPR_GLOBAL_MAP` already uses for score, because
these get substituted into arbitrary expressions *including an `if` condition*,
where there is nowhere to hang an import. Globals also join the Android
Activity-restart save file, or a room switch there would keep the score and
silently forget every global.

Multiplayer identity globals still read 0/false on Kivy, which stays correct —
nothing writes them, because a Kivy export never networks.

**Two adjacent bugs found and deliberately NOT fixed** (out of scope, recorded
in `TODO.md` for a separate decision): `set_variable` with a `self.`-prefixed
name emits `self.self.coins`, and a non-global value *expression* is emitted as
a string literal, so `coins + 1` assigns the text `"coins + 1"` rather than
incrementing.
