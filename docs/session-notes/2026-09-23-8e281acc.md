## [2026-10-07] User

> Answer the following question do not implement
> Would it be possible to use the sprite used by a wall object as a tile in the raycast view?

### Claude

**Yes — and it's already implemented, not a gap.** When `build_raycast_walls` derives a wall edge from a solid instance, it records which instance made it and remembers that instance's own sprite (`inst.sprite`) alongside the edge, keyed per-edge (`v_sprites`/`h_sprites`). At render time, each wall strip is textured with:

```
tex_sprite = wall_texture_override  if the camera set one,  else  that edge's own wall sprite
```

So if a wall object's `enable_raycast_view` call leaves `wall_texture` empty (it's an optional param, not required), every wall strip samples the texture straight from whatever sprite is assigned to the wall *object* that built it — the exact same sprite the student already sees in the 2D top-down editor, with zero extra authoring. I confirmed this fallback exists identically in all three renderers (desktop `renderer.py`, HTML5 `export_html5.js`, Kivy `export_kivy.py`), so it's not desktop-only.

Practical upshot, worth knowing: if a maze uses **more than one wall object/sprite** (say `obj_wall_brick` vs. `obj_wall_moss`, the kind of visual variety a student would naturally add to a 2D maze), the 2.5D view already shows each one with its own distinct texture automatically — no "unify into one wall_texture sprite" step needed. The global `wall_texture` override exists for the opposite case: forcing one uniform look (what `raycast_1`–`4` do with their dedicated texture sprites) regardless of how many different wall objects are actually placed.

Two honest caveats:
- **Shared-edge tie-break**: if two different wall instances happen to contribute to the exact same grid edge, whichever one the renderer iterates last "wins" that edge's texture — not an issue in the normal one-wall-per-cell-edge case.
- **Always frame 0**: texturing always samples `get_frame(0)` of the sprite, not the instance's live `image_index` — an animated wall sprite would show only its first frame in the 3D view, never animate there.

To your question: yes, it's very doable. The trick is picking mechanics that are inherently variable-free rather than trying to hide variables from the student.

Good building blocks that need zero variables:
- **Collision-based scoring**: `test_instance_count` on a target object checks win conditions without the student ever touching a counter — "if no more fruit exists, show Win." The engine still tracks a count internally, but the student never declares, reads, or increments one.
- **`destroy_instance`** on collision for "collect the fruit" — no score variable needed if the win condition is "all fruit gone" rather than "score reaches N."
- **Direct instance actions** (`move_towards_point`, `set_direction_speed`, `jump_to`) — motion without `x`/`y` variables being exposed to the student.
- **Alarms and timers** as pure events — "after 2 seconds, do X" needs no variable to author, even though one exists under the hood.
- **`set_lives`/`draw_lives`** — this one still *is* a variable conceptually, but it's pre-named and pre-wired as a single action, not something the student assembles from a separate "create variable" step. Same for score, actually — if the tutorial only ever says "add 10 to score" as one opaque action block and never asks the student to read, store, or compare it, most 9-10 year olds experience it as "a point counter," not as algebra.

The real distinction for this age group usually isn't "variables: yes/no" but "does the student ever have to create, name, or reason about a variable's current value to make a decision." A tutorial built entirely from collision → destroy/spawn → count-based win/lose, with score/lives treated as a single fire-and-forget action rather than something inspected, can avoid that entirely.

So: a "catch the fruit, avoid the bomb" tutorial using only collision events + destroy_instance + test_instance_count (or test_lives, pre-wired) is realistic without ever surfacing the concept of a variable to the student, even though score/lives exist as plumbing.
