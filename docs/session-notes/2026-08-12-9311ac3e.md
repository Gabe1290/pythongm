## [2026-08-12] User

> we have a 2.5 D Doom-like extension. Would it be possible to do something like a Minecraft extension because students are very excited about Minecraft. Are the any copyright issue I should be aware of? Just answer do not implement

### Claude

Short answer: technically yes, legally you need to be careful about how you frame it.

**Feasible?** Very. A voxel-world extension (place/break cubes, chunked grid, simple textures) fits the same folder-extension pattern as `raycast_2_5d` — new room-renderer + actions, no core changes. It's a bigger lift than the raycast work (chunk meshing/culling for performance, inventory UI, world persistence) but nothing exotic.

**Copyright/trademark issues to actually watch:**
- **"Minecraft" the name/logo** — trademarked by Mojang/Microsoft. Don't call it that, don't use their logo or branding, don't market it as Minecraft-compatible. Call it something generic ("Block World," "Voxel Builder").
- **Original textures/assets** — Minecraft's actual texture files (grass block, dirt, etc.) and its distinctive font are copyrighted. Don't ship or bundle real Minecraft textures/sounds. Hand-drawn/original pixel art in a similar blocky style is fine — the general *aesthetic* of low-res voxel cubes isn't ownable, only the specific expression is.
- **Mechanics/gameplay concepts** — game mechanics themselves (place/break blocks, crafting, survival loop) are not copyrightable. Clone Wars-style "blocky sandbox building game" clones are extremely common and legal (Minetest/Luanti is a well-known fully open-source example). This is the safe territory.
- **`.minecraft` world/mod file formats** — if you ever import real Minecraft world saves or resource packs, that's importing copyrighted third-party content, different risk profile than building your own format.

Bottom line: build your own voxel engine with original art and a different name, and you're in "inspired by" territory same as Minetale/Terasology/Minetest — no copyright problem. The risk only shows up if you use their name/logo or their actual asset files.

> I want to steer clear of any copyright issues with Minecraft. Can we base it on Luanti?

### Claude

Architecturally, no — Luanti is a separate C++/Lua engine, not something you can import into a Python/PySide6 codebase; "basing it on Luanti" in practice would mean writing your own voxel engine (same pattern as the raycast extension) while borrowing ideas from its node-based world format, not forking its code.

Where Luanti *is* directly useful is its assets: the engine itself is LGPL (fine to be inspired by, awkward to actually embed), but block textures from Minetest Game and community packs are usually CC0 or CC-BY-SA — CC0 ones you can drop in freely, CC-BY-SA ones require attribution and share-alike (any exported student game bundling them would need to stay CC-BY-SA too, which could be a headache for a "kids export their game" tool). My recommendation: build the engine from scratch like raycast_2_5d, and only pull in specific CC0-licensed Luanti/Minetest texture packs for block art (checking each pack's license individually) rather than treating "based on Luanti" as reusing its codebase.

## [2026-08-13] User

> what is the the pitch-picking fix

### Claude

The core problem: `handlers.py`'s `_pick` (line ~63) never reads `cfg.get("pitch")` at all — it calls `pick_block` with a flat horizontal ray at a fixed layer, regardless of what `set_look_pitch` has done to the view. So tilting up/down changes what you *see* but not what `place_block`/`break_block` *target*.

The fix isn't a one-line swap, though — there's a real wrinkle I want to flag before touching it:

**What's already there to use:** `screen_ray(sx, sy, ...)` converts a screen pixel into `(angle, z_per_px)` — the same thing the preview tool uses for mouse-aim. For the crosshair (no mouse, always screen-center), the ray would be `screen_ray(screen_w/2, screen_h/2, ..., horizon=horizon_for(screen_h, pitch))`. When pitch is 0, that reduces to `z_per_px=0` — an exactly-horizontal ray, same as today. When pitch is nonzero, `z_per_px` comes out nonzero and the ray actually tilts with the view. Then `pick_voxel(room, cam_x, cam_y, eye_z, angle, z_per_px, ...)` marches it in 3D and returns `(target, placement)` in the same `(x, y, z)` shape `pick_block` already returns — so `execute_place_block_action`/`execute_break_block_action` downstream don't need to change at all.

**The wrinkle:** `pick_block` has a specific "prefer refilling a gap" rule — added after a playtest found that without it, a hole knocked in a wall could never be refilled (the placement lands somewhere past the hole instead of in it). `pick_voxel` has no such rule; it just tracks the single previous empty cell. At `z_per_px=0` those aren't the same thing whenever the ray passes over more open floor *beyond* the hole before hitting something else — `pick_block` still remembers the hole via its dedicated `gap` tracking, `pick_voxel` would forget it and place wherever the ray actually stopped. A naive swap would quietly re-break the exact bug `ecb319c` fixed.

So the real fix is: either port that gap-preference into `pick_voxel` (or a 3D-aware version of it) before switching `_pick` over, or consciously accept/document that pitched picking loses the gap heuristic. I'd also need to plumb screen width/height into `_pick` (it runs game-logic side, no direct render surface — same pattern `draw_doom_hud`'s handler already uses via `game_runner.window_width/height`).

Want me to go ahead — and if so, port the gap rule into 3D picking, or ship without it and note the tradeoff?
