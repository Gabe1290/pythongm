## [2026-09-23] User

> One problem my students encoutered is that they start up a second instance of the PyGameMaker IDE after closing the windows used fore testing a game. Would it be possible to force the Game Window in front of the IDE ? The same thing happens when editing a sprite and selecting a color. The selection window can de hidden behing the IDE if a student clicks on the IDE and the student cannot get back to the color selection. Just answer the question, do not implement

### Claude

Yes to both, with different reliability:

**Game window "always on top":** technically possible via a window-manager hint (`_NET_WM_STATE_ABOVE` on X11, which most Linux WMs honor for an app requesting it for itself). But this is the same category of limitation we hit with the IDE-restore fix: on Wayland (which many current Ubuntu/Linux Mint defaults use), there is **no** client-side API for a window to force itself above another app's window — it's deliberately not offered, for the same anti-abuse reason background apps can't steal focus. So it would likely work on an X11 lab machine and silently do nothing on a Wayland one. Worth trying, but not a guaranteed fix depending on what the lab actually runs.

**Color picker:** better news here. `QColorDialog.getColor(...)` (what both call sites use) is already **application-modal** by default — which is *supposed* to prevent exactly this, since a modal dialog should stay above and own all input focus while open. The fact it still gets buried means the window manager isn't honoring that modal/parent relationship for stacking (plausible on some Wayland compositors, or certain WMs generally). This case is more fixable than the game window, though, because it's our own Qt code in the same process — we have real levers here (e.g. an explicit "stay on top" hint on the dialog, or catching the moment the IDE regains focus while a modal child is open and re-raising it) that don't depend on cross-process/cross-app focus-stealing permissions the way the pygame window does. Also worth noting: because the dialog is modal, a student who buries it is doubly stuck — the IDE is unusable (blocked by the modal dialog) *and* the dialog is invisible, with no way to alt-tab back to it either. That's a worse trap than the game-window case.

**On the duplicate-IDE-instance symptom specifically:** independent of fixing focus, a single-instance guard (detect an already-running IDE and just raise/focus that instance instead of launching a second process) would directly prevent students from ending up with two IDEs open — and that one is WM-agnostic, so it'd work reliably everywhere regardless of X11 vs Wayland. Worth considering as a complementary fix even if the focus issue itself stays partially unsolved on some machines.
